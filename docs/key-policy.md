# Політика керування ключами

## 1. Генерація ключів

* Усі секрети генеруються **лише CSPRNG**: `secrets.token_bytes()` (ОС: `getrandom`/`/dev/urandom`)
  або генераторами бібліотеки `cryptography` (OpenSSL RAND).
* Симетричні майстер-ключі: AES-128/192/256 (`SymKeyStore.new`, за замовчуванням 256 біт).
* RSA: 2048/3072/4096 біт, e = 65537 (рекомендовано ≥ 3072 для нових ключів).
* ECC: криві NIST P-256 і P-384.
* Ідентифікатор ключа `key_id` — 8 випадкових байт у hex; він не розкриває вміст ключа.
* Модуль `random`, час, PID тощо як джерело ключів **заборонені**.

## 2. Salt і HKDF — унікальний ключ для кожного файлу

Майстер-ключ ніколи не використовується для шифрування напряму:

```
salt   = token_bytes(16)                         # новий для кожного файлу
okm    = HKDF-SHA256(master, salt, info="CSYM-v1|<MODE>|<key_id>")
enc_key, mac_key = okm[:n], okm[n:]              # окремі ключі для шифрування та MAC
```

* Розділення доменів через `info` (режим + key_id) не дозволяє використати ключ одного режиму в іншому.
* Для CBC/CTR ключі шифрування та HMAC різні (32 Б mac_key).

## 3. Зберігання

### Сховище симетричних ключів `keystore.json`

```
KEK      = scrypt(password, salt=16 Б, N=2^15, r=8, p=1, len=32)
check    = nonce12 | AES-GCM(KEK, "crypto-suite keystore v1", AAD="check")   # перевірка пароля
wrapped  = nonce12 | AES-GCM(KEK, master_key, AAD=key_id)                     # кожен ключ окремо
```

* У файлі зберігаються лише метадані та **обгорнуті** ключі; відкритих ключів немає.
* AAD = key_id прив'язує обгорнутий ключ до свого запису (підміна записів виявляється).
* Неправильний пароль → `BadPassword` (за перевірочним блоком `check`).
* Запис атомарний (`*.part` → `os.replace`), права файлу 0600.
* `keystore.json` у `.gitignore` — **ніколи не комітиться**.

### Приватні ключі RSA/ECC

* Лише PKCS#8 PEM, зашифрований паролем (`BestAvailableEncryption`); без пароля зберегти неможливо (`BadPassword`).
* Файл створюється з правами 0600; `keys/*.pem` у `.gitignore`.
* Публічні ключі — відкритий SubjectPublicKeyInfo PEM.

### Паролі

* Передаються аргументом, змінною середовища (`CRYPTO_SUITE_KS_PASSWORD`, `CRYPTO_SUITE_KEY_PASSWORD`)
  або вводяться через `getpass`. У логи не потрапляють (логер маскує `password`, `key`, `nonce`, `iv`, `tag`, `salt`, `data`, ...).

## 4. Ротація

Кожен ключ має метадані: `created`, `expires` (за замовчуванням 90 днів), `uses`, `max_uses` (за замовчуванням 1000), `status`.

| Тригер | Дія |
|---|---|
| ручна команда `sym rotate --label L` | усі `active` ключі мітки → `retired`, створюється новий `active` |
| `uses >= max_uses` (лічильник шифрувань) | при шифруванні за міткою — **авторотація** (подія `keystore.auto_rotate` у лозі) |
| `now >= expires` (строк дії) | те саме — авторотація |
| явний `key_id` вичерпаного/retired ключа | `KeyPolicyViolation` — шифрування заборонено |

* `retired` ключ **не шифрує**, але **розшифровує** старі дані (їх можна поступово перешифрувати).
* Лічильник `uses` збільшується до шифрування і зберігається на диск.

## 5. Відкликання

* `sym revoke --key-id ID --reason compromised` → статус `revoked`.
* `revoked` ключ **не шифрує і не розшифровує** → `KeyPolicyViolation`, подія `keystore.decrypt_denied`.
* Відкликання застосовується при компрометації; дані, зашифровані таким ключем, вважаються скомпрометованими.

## 6. Заборона повторного nonce/IV

* Nonce/IV генерується CSPRNG для **кожної** операції: GCM 96 біт, CCM 104 біти, CTR 128 біт, CBC IV 128 біт.
* Додатково ключ файлу унікальний завдяки 128-бітному salt HKDF, тому навіть випадковий збіг nonce
  не призводить до повторного використання пари (ключ, nonce).
* API не дозволяє передати nonce ззовні — повторне використання неможливе на рівні інтерфейсу.
* Ліміт `max_uses` додатково обмежує обсяг даних під одним майстер-ключем.
